## Bugs

- [x] 2026-08-12 — **Regression, shipped in v2.0.0 as published:** Help > About WordMD crashed the whole app. `MenuAbout_Click` is `async void`, so the unhandled exception had nowhere to propagate and killed the process. Root cause: `SecondaryTextBrush()` (added same day for the tip-jar disclaimer text) indexed `Application.Current.Resources.ThemeDictionaries` directly with no guard; it threw at runtime despite compiling cleanly and matching Microsoft's documented shape — neither proves the actual resource structure on a real machine matches the docs, and this code path had never run in a live app before, since the machine building it has no .NET SDK. Fixed same day: `SecondaryTextBrush()` is now `TryGetValue`-defensive at every step with a guaranteed-safe literal fallback, and `MenuAbout_Click` wraps the whole dialog in try/catch as a permanent backstop. **Patched as v2.0.1** (JJ, 2026-08-12): v2.0.0's tag stays exactly what it says — a real, if broken, build, not silently rewritten — and v2.0.1 becomes `releases/latest` so new downloaders get the fix automatically. JJ was the only person who downloaded v2.0.0. Worth a broader look eventually: 12 other `async void` Click handlers in `MainWindow.xaml.cs` share the same structural risk (unhandled exception = whole-app crash), though only this one is newly-written, never-runtime-verified code; the other 12 have run in production across multiple releases without incident.

## Done

- [x] (S)(M) Copy-to-clipboard button on fenced code blocks in the formatted pane, 2026-08-12. JJ: "add a copy icon to code blocks... takes that whole block into the clipboard." Implemented as a ProseMirror NodeView (`web/src/milkdown-host.ts`), not a MutationObserver appending a button into the rendered `<pre>` — that was tried first and hung the renderer: ProseMirror runs its own DOM-reconciliation observer, and a foreign node appended inside content it manages triggers a synchronous mutation fight between the two observers. The NodeView gives ProseMirror a `contentDOM` (`<code>`) it owns and reconciles normally, with the button as an untouched sibling inside `dom` but outside `contentDOM`. `stopEvent` is scoped to just the button (not the whole block), so typing/clicking/selecting inside the code text is unaffected — verified directly (typed into a code block post-change, confirmed the edit landed correctly and round-tripped through the markdown serializer). Excluded from print via `editor.css`'s existing `@media print` chrome-exclusion block, since print clones the live DOM. Clipboard write itself is unverified end-to-end (this browser-automation environment structurally denies `clipboard.writeText` regardless of click authenticity — confirmed via a bare, unrelated call failing the same way), but WebView2's default policy allows a user-gesture clipboard write with no extra permission grant, confirmed earlier in this session when checking for related permission handling in `MainWindow.xaml.cs` (none exists, none needed).
